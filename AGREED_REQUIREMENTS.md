# Действующие требования к аудитору каталога

Дата обновления: 27.10.2026 (Asia/Qyzylorda).

Этот файл содержит только актуальные решения пользователя. История обсуждений находится в `plans/archive/requirements_history_2026-10-27.md` и не читается без конкретной необходимости. Требования не разрешают Stage 5/6, изменение `core`, whitelist или запись в production.

## Назначение и результат

- Аудитор находит фактические ошибки карточек `shop.telecom.kz` и предлагает исправления. Добавление новых товаров — отдельная задача.
- По каждому полю различать: подтверждено, найдено расхождение, в эталоне нет значения, проверка не выполнена с конкретной причиной.
- Отсутствие значения в эталоне не является ошибкой магазина. Из общего счётчика совпадений нельзя угадывать состояние остальных полей.
- Цитаты и ссылки сохраняются. Предложение без достаточного доказательства не применяется.
- Результат аудита и состояние обработки менеджером — разные вещи.

## Варианты товара

- Чистое региональное обозначение само по себе не участвует в идентичности товара. Сравнивать модель, аппаратную версию и реальные характеристики.
- Если региональные версии имеют подтверждённое техническое различие, учитывать само различие, а не название региона.
- SIM-конфигурация, поколение связи и аппаратная ревизия существенны. Такие варианты нельзя автоматически объединять.
- Не удалять произвольные суффиксы: заводской код и ревизия могут быть частью модели.
- Одно правило действует в группировке, поисковом запросе и проверке эталона. Не исправлять только промпт, оставляя противоположную группировку.

## Недостающие характеристики

- Предлагать важные для покупателя характеристики с учётом типа товара.
- Допустимы прямо подтверждённые отрицательные значения, например `NFC: нет`; примеры не образуют закрытый список.
- Если функция не упомянута в эталоне, ничего о ней не выводить и не сохранять. Молчание источника не означает отсутствие функции.
- Не использовать условия, списки исключений или смысловые регулярные выражения под конкретные товары и названия полей.
- Для предложения обязательны название, значение, точная цитата и ссылка. Цитата должна присутствовать в реально переданном тексте эталона.

## Сравнение, режимы и объём данных

- `2.5` отличается от `25`; `2.5` и `2,5` равнозначны; `2500 Мбит/с` и `2.5 Гбит/с` равнозначны.
- `--skip-tech` не сравнивает характеристики и не стирает прежний результат; описание может потребовать модель.
- `--skip-desc` не проверяет описание и не стирает прежний результат.
- `--photos-only` проверяет только количество фото подходящего эталона, сохраняет остальные результаты, не изображает характеристики проверенными и не мешает будущей полной проверке.
- `--skip-audited` учитывает фактически выполненные части и актуальность их входов. Старые строки с неизвестным покрытием нельзя объявлять полностью проверенными.
- Лимит текста эталона для модели остаётся 25 000 символов; описание магазина ограничивается отдельно. DOM браузера — не более 50 000 символов.
- Обычный кэш ссылок и текстов — 14 дней. Это не срок хранения отчётов.
- Каскад поиска и приоритет Kaspi сохраняются. Сравнение нескольких независимых источников — отдельный будущий эксперимент.

## Базы и сохранение

- Используются две базы: локальная SQLite Python-сервиса и тестовая MySQL магазина через VPN. Третья обязательная БД не нужна.
- MySQL для Python строго read-only. Локальная SQLite хранит отчёты и сохраняется JIT по правилам `AGENTS.md`.
- Перед любой будущей тестовой записью нужно подтвердить конкретное подключение и целевую БД. Работающий VPN сам по себе не определяет среду.
- Не записывать проверки в исходную SQLite: использовать отдельную копию с учётом WAL.

## Будущая админка и доступ

- Рабочее место менеджера: таблица и просторное двухколоночное окно «магазин / эталон» в существующей админке `core`.
- Сотрудники раздела контента работают с результатами. Запускать и повторять аудит могут только Дамир и два разработчика. Полный технический след доступен только Дамиру.
- Ограничения обеспечиваются сервером. Менеджерам не показываются токены, стоимость, тайминги и полный search trace.
- Фото и описание в первой версии только показываются; автоматически меняются только отдельно подтверждённые технические характеристики.

## Будущий «Апрув»

- Менеджер выбирает каждое замечание отдельно и может отредактировать предложенное значение до сохранения.
- Laravel перед записью сравнивает текущее значение с состоянием на момент аудита и защищает проверку вместе с записью от гонки.
- Конфликт одного поля не блокирует остальные подтверждённые исправления. Конфликтное поле не перезаписывается и остаётся нерешённым.
- Для конфликта показываются значение на момент аудита, текущее и предложенное. После нового решения актуальность поля проверяется снова.
- Состояния `не обработано / частично обработано / обработано` отделены от исходного результата аудита.
- Если MySQL сохранил изменение, а Python не получил подтверждение, повторяется доставка результата без повторного изменения товара. Python распознаёт повтор операции.
- Если Python недоступен, интерфейс показывает понятное сообщение без подмены БД, старых данных и обхода прав.
- Конкретные поля, права `core`, протокол доставки, сервер, резервное копирование и production требуют отдельных планов и разрешений.

## Процесс разработки

- Каждый этап получает отдельный план с файлами, потоком данных, рисками, проверками и точным ожидаемым терминальным выводом, если он меняется.
- Основной агент чата сам реализует этап, проверяет полный diff и один раз запускает полный `verify-gate` на итоговом состоянии. Субагенты требуют отдельного разрешения Дамира.
- После автоматических и разрешённых настоящих проверок агент даёт пошаговую инструкцию для личного теста. Следующий этап начинается только после успешной проверки Дамиром и прямого разрешения.
- Не делать общий рефакторинг и не расширять согласованный этап скрытыми исправлениями.
