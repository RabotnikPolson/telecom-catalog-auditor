## 1. ПАСПОРТ ПРОЕКТА И БИЗНЕС-ЦЕЛИ

### 1.1. Назначение системы
Автономный Python-микросервис для регулярного ночного аудита технических характеристик (ТХ) каталога `shop.telecom.kz` (~20 000 товаров). 
* **Главный фокус системы:** **Фактологический арбитраж (Fact Checking & Accuracy Audit)** — автоматическая сверка существующих значений параметров карточки магазина с внешними эталонами, выявление опечаток, расхождений и ошибок поставщиков. *(Примечание: аудит пропущенных обязательных полей вынесен за рамки MVP по требованию заказчика).*
* **Инкрементальность:** Поддержка умного пропуска ранее проверенных товаров через хэширование данных (`content_hash`), чтобы не тратить ресурсы на повторную проверку неизменных карточек.

### 1.2. Фундаментальные ограничения безопасности
* **Zero-Write Policy (Без прямого авто-апдейта):** Сервис **не имеет прав записи** в боевую БД сайта (`telecom.kz`). Все результаты передаются в виде структурированных отчетов (.xlsx) или через защищенный Read-API для админки Laravel.
* **Zero-Impact Policy (Бережный ночной сбор):** Сбор данных с витрины `shop.telecom.kz` выполняется в ночное окно (02:00 – 06:00 UTC+5) в щадящем режиме (2–3 потока с задержкой), чтобы исключить любую нагрузку на боевой сервер.
* **Строгий Grounding (Защита от галлюцинаций):** LLM работает исключительно как независимый арбитр (Judge) по переданному тексту веб-страницы. Выдумывать характеристики «из памяти» запрещено на уровне промпта и схемы валидации.
* **Обязательный Audit Trail:** Любой вердикт об ошибке обязан содержать точную цитату (`proof_quote`) и URL-источник (`source_url`).

## 3. ДЕТАЛЬНОЕ ОПИСАНИЕ ПОДСИСТЕМ

### 3.1. Ночной сборщик каталога (Night Telecom Crawler)
Для автономного получения актуального каталога без зависимости от ручных выгрузок:
1. **Дерево разделов через прямой JSON API:**
   * Сервис запрашивает внутренний эндпоинт `GET https://shop.telecom.kz/getAllCategories`.
   * Получает древовидную структуру категорий (Смартфоны, Роутеры, Видеонаблюдение и др.) с их `urlkey` и идентификаторами без парсинга тяжелого HTML.
2. **Обход витрины с пагинацией:**
   * Проход по каталожным разделам `https://shop.telecom.kz/catalogue/{category}/{subcategory}/{group}?page={N}`.
   * Парсинг карточек товаров на странице: `product_id`, `title`, `current_specs` (блок ТХ), `vendor_sku`, `manufacturer_sku`.
3. **Режим бережной ночной работы (Rate Limiting):**
   * Расписание запуска: 02:00 – 05:00 (минимальная посещаемость магазина).
   * Concurrency: не более 2–3 параллельных HTTP-запросов.
   * Jitter: случайная пауза 0.6–1.5 секунды между страницами.
4. **Управление состоянием (State Resume):**
   * Прогресс сканирования фиксируется в таблице `crawler_state`. При сетевом сбое краулер возобновляет работу с прерванной страницы, не начиная сначала.
5. **Сверка на лету через `content_hash`:**
   * Если товар уже есть в базе со статусом `VERIFIED` и его `content_hash` совпадает — карточка не сбрасывается в повторный аудит.
   * Если товар новый или характеристики изменены контентщиками — карточка сохраняется со статусом `PENDING`.

### 3.2. Инкрементальный аудит (content_hash)
* В сущность `Product` и таблицу `products` внедрено поле `content_hash: str`.
* Хэш рассчитывается как SHA-256 от детерминированной строки:
  `f"{title.strip().lower()}|" + "|".join(f"{k.strip().lower()}:{v.strip().lower()}" for k, v in sorted(current_specs.items()))`.
* **Правило пропуска:** Если товар уже имеет статус `VERIFIED` и его текущий `content_hash` совпадает с хэшем в базе аудита — товар немедленно пропускается без обращений к внешним сервисам (0 сек, 0$).

### 3.3. Модуль дедупликации (Parent-Child Grouper)
* Из 20 000 товаров каталога выделяются уникальные Master-модели через нормализацию названия (удаление цветов и комплектаций):
  `iPhone 13 128GB Midnight` ➔ Master-ключ: `apple_iphone_13_128gb`.
* **Аппаратная защита памяти:** Память (128GB, 256GB, 512GB) строго изолируется и не склеивается.
* Внешний поиск и краулинг выполняются **один раз на группу**.
* Child-модификации (другие цвета) наследуют базовые характеристики, локальный строковый regex сверяет только атрибут `Цвет`.

### 3.4. Каскадное получение эталонной ссылки
1. **Прямой шаблон поставщика (Zero-Cost / Без Serper):**
   * Если в карточке указан поставщик (`vendor_name`) и есть артикул (`vendor_sku`):
   * Ссылка формируется по шаблону из словаря `VENDOR_PROFILES`:
     `url = VENDOR_PROFILES[vendor_name]["search_url_template"].format(vendor_sku=vendor_sku)`.
   * Поисковик Serper не вызывается (0$, 0 сек).
2. **Навигационный поиск через Serper API (Google KZ):**
   * Подключается при отсутствии прямого шаблона вендора.
   * Поиск официального сайта бренда или маркетплейсов Kaspi / DNS (`gl="kz"`, `hl="ru"`).
   * Жесткая Whitelist-фильтрация доменов (отсекаются форумы, спам и блоги).

### 3.5. Сбор и экстракция ТХ (Crawl4AI + Gemini Extractor)
* Локальный headless-браузер (Chromium на Playwright) заходит по полученному URL.
* Раскрывает вкладки спецификаций, отрабатывает клиентский JS (React/Vue).
* Gemini Extractor переводит очищенный Markdown страницы в структурированный JSON эталона.

### 3.6. Двухуровневое кэширование в SQLite
База `catalog_audit.db` (режим WAL) хранит два слоя кэша:
1. `url_cache`: связка `(query_hash ➔ resolved_url)` — исключает повторный поиск в Google KZ.
2. `specs_cache`: связка `(resolved_url ➔ specs_json)` — исключает повторный запуск браузера по уже спарсенным адресам.

### 3.7. Фактологический арбитраж (LLM-as-a-Judge)
* Gemini Flash Lite сопоставляет только **существующие характеристики** с сайта `shop.telecom.kz` с эталонным JSON от Crawl4AI.
* Учитывает синонимы и единицы измерения.
* Возвращает структурированный вердикт: статус (Зеленый, Желтый, Красный), `confidence_score`, `proof_quote` и `source_url`.

### 3.8. Двойной интерфейс доставки (Dual Delivery)
* **Для контент-отдела и руководства:** Форматированный интерактивный Excel (.xlsx) с подсветкой ячеек по коридорам и ссылками.
* **Для Laravel Биржана:** REST API на FastAPI (`POST /api/v1/audit/check-product`) с OpenAPI/Swagger (`/docs`).
